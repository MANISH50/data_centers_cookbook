Beginner Chapter 01

What is a large language model?

A machine that has read so much text that it became very, very good at one game: guessing what comes next.

Every answer Claude writes is built one small piece at a time. It looks at everything so far, then predicts the piece that should come next.

How models like this work A large language model () is a computer program that takes in text and predicts what text should follow. Your phone keyboard does a tiny version of this when it suggests the next word.

An LLM does the same thing, but it has learned from a huge amount of writing, so its guesses can carry on a whole conversation, write code, or explain a hard idea.

“Large” means two things: it learned from an enormous library of text, and it is made of a huge number of adjustable numbers called . You’ll meet both in Part B.

Cleaning

Washing the data

Anthropic has said ↗ Anthropic says it used “several data cleaning and filtering methods, including deduplication and classification.”

How models like this work In general, cleaning pipelines for language models work roughly like this:

  1. Extract the text. Strip menus, ads and page code, keeping the readable words.
  2. Remove duplicates (). The same text copied on a thousand sites would otherwise be learned a thousand times.
  3. Classify and filter. Small models score each page for quality, language and harmful content, and low scores are dropped.
  4. Mix. Decide how much code, science, conversation and so on goes into the final recipe.

Beginner Chapter 04

Tokens

The tiny pieces every sentence is broken into, and why they decide both what a model can read and what you pay.

A model never sees letters the way you do. It sees tokens: small chunks of text, each one swapped for a number.

How models like this work A cuts text into . A common word like “the” is often one token. A rare word like “unbelievably” may become three: “un”, “believ”, “ably”. Spaces and punctuation count too.

Each token has an ID number from the model’s , a fixed list of all the pieces it knows. So “Hello world” might become something like [9906, 1917]. Only numbers go into the model.

Think of LEGO: a model doesn’t build with whole houses, it builds with a fixed set of bricks. Common shapes get their own brick; rare shapes are made from several.

Intermediate Chapter 05

The Transformer

Embeddings, attention, layers and parameters: the recipe inside almost every modern language model.

In 2017, a research paper with a bold title, “Attention Is All You Need”, gave the world the recipe nearly every language model still follows.

How models like this work ↗ The paper introduced the . Its big idea: let every word look at every other word at the same time, instead of reading strictly left to right. That made models both smarter and much faster to train on parallel chips.

Anthropic hasn’t published the full design of Claude, but it describes Claude as a large language model, and Transformer-style designs are the standard for these. Scroll on to walk through one, step by step.

Illustration

1 · Tokens in

The sentence “The cat sat on the …” arrives as token IDs, the numbers from Chapter 4.

2 · Each token becomes a list of numbers

Every ID is swapped for an : a long list of numbers that stands for its meaning. Words used in similar ways get similar lists. Position is added too, so the model knows the word order.

3 · Attention: words look at each other

Each token asks “which other tokens matter to me?” and mixes in information from them. “sat” pays a lot of attention to “cat”, because cats are who sat. This is .

4 · A small thinking block

Next, each token’s numbers go through a small calculation block (a “feed-forward network”) that refines what it means, using what the model learned in training.

5 · Repeat, many times

Attention + thinking block = one . A big model stacks many layers, each refining the picture further, like an assembly line where every station adds detail.

6 · Predict the next token

At the top, the model scores every token in its vocabulary. “mat” scores high, “idea” low. One is picked, added to the text, and the whole process runs again for the next token.

Intermediate Chapter 06

Pre-training

Hide the next word. Guess it. Check. Adjust. Repeat, an unimaginable number of times, on thousands of chips at once.

Photo: Fukumoto · Wikimedia Commons · CC BY-SA 4.0

Training a model is like a student reading millions of books and practising guessing the next word, again and again, until the guesses get very good.

How models like this work At the start, all the are random numbers, so the model’s guesses are nonsense. Then the practice loop begins:

  1. Show the model a stretch of real text with the next token hidden.
  2. Guess. The model gives a score to every possible next token.
  3. Check. Compare with the real next token. The size of the mistake is the .
  4. Adjust. Work out which way to nudge every parameter to make that mistake smaller (the ), and nudge them all a tiny bit.

Repeat across trillions of tokens, in giant batches. This first, enormous stage is .

Scaling laws

Bigger, more data, more compute

How models like this work ↗ In 2020, researchers found that a language model’s loss falls in a smooth, predictable way as you grow three things together: the number of parameters, the amount of training data and the compute spent.

How models like this work ↗ A 2022 study (“Chinchilla”) showed many models were too big for the data they saw: for a fixed compute budget, a balanced mix of model size and data does better.

That predictability is why AI companies invest in ever-bigger clusters: they can roughly forecast what more compute will buy.

Why AI needs special chips

GPUs, TPUs and Trainium: chips built to do one kind of maths, unbelievably fast, millions of times in parallel.

Photo: Enrique Jiménez · Wikimedia Commons · CC BY-SA 2.0

A normal computer chip is a brilliant all-rounder. An AI chip is a specialist: it does one kind of sum, and does a mountain of them at once.

How models like this work Almost all of a language model’s work is multiplying big grids of numbers (matrices): the token’s numbers times the model’s parameters, layer after layer. Each little multiplication is easy. There are just billions of them for every token.

A CPU, the chip in your laptop, has a few very smart cores that do tasks one after another. An has thousands of simpler maths units that work side by side. For grid maths, side by side wins by a mile.

🧠 Accelerators (×8)

The stars: GPUs, TPUs or Trainium chips that do the model’s grid maths. Each one holds part of the model and works on it in parallel with the others.

Daily life: eight chefs at eight stoves, cooking one giant meal together.

⚡ High-bandwidth memory

Stacks of very fast memory packed right next to each accelerator. The model’s parameters live here. AWS has said ↗ Each Trainium3 chip has 144 GB of HBM3e.

Daily life: ingredients on the chef’s counter, not in the basement.

🔗 Chip-to-chip links

Private, very fast highways so the accelerators can share results directly: NVIDIA calls them NVLink, Google ICI, AWS NeuronLink. Amazon has said ↗ In Project Rainier, blue NeuronLink cables join 4 servers × 16 Trainium2 chips into one 64-chip “UltraServer”.

🧮 CPUs

Ordinary processors that run the operating system, prepare work, tokenize text and feed the accelerators. NVIDIA has said ↗ Its GB200 “superchip” pairs one Grace CPU with two Blackwell GPUs.

📦 System memory

Normal server RAM for the CPUs: plenty of it, but much slower than HBM. Used for staging data and running the software around the model.

🌐 Network cards

How models like this work AI servers typically have one fast network card per accelerator, so every chip can talk to chips in other servers during training. One or two more connect to storage and the rest of the data center.

💾 NVMe SSDs

Fast local drives for the operating system, model files and checkpoints, so a restart can load quickly.

🔌 Power supplies

How models like this work Several redundant power supplies convert the rack’s power for the server. A fully loaded 8-accelerator server can draw on the order of 10+ kilowatts, like a few household ovens on full.

🌀 Fans

Rows of powerful fans push air through the server. In liquid-cooled designs, fans have less to do because most heat leaves through liquid.

❄️ Heat sinks and cold plates

Each accelerator is covered by a big metal heat sink (air-cooled) or a cold plate with liquid flowing through it (liquid-cooled). Chapter 12 explains why AI is moving to liquid.

Splitting the work

Three ways to share one giant job

📚

Data parallelism

How models like this work Many groups of chips each hold the model and learn from different pages of the data, then share what they learned. Like many students reading different chapters, then comparing notes.

🧱

Claude API basics

Messages, system prompts, tokens and price: everything you need for your first call, and to know what it will cost.

Talking to Claude from code is like sending a very well-organised letter: who you are, what you want, and how long a reply you’ll accept.

Anthropic has said ↗ Apps talk to Claude through the Messages API. Each request contains:

  • model: which Claude to use, such as claude-opus-5-5.

Faster and cheaper

      
Prompt caching, batching, the right model and the right effort: the levers that cut bills and waiting times.

    

    
Photo: Роман Рябенко · Wikimedia Commons · CC0

  


  

    
Most apps send the same long instructions and documents again and again. Paying full price to re-read them every time is like reprinting the whole menu for every customer.

    

      
Anthropic has said ↗  lets you mark the start of your prompt (system prompt, tools, documents) so Claude stores the processed version. Later requests that begin with exactly the same text read it from the cache, which costs less and responds faster. Cached entries last 5 minutes by default, or 1 hour if you choose.

      
Anthropic has said ↗ A cache write costs 1.25× the normal input price (2× for the 1-hour cache). A cache read costs much less: on Claude Opus 5.5, $0.20 per million tokens instead of $4.

Python · Azure Function calling Claude in Microsoft Foundry
import os
from anthropic import AnthropicFoundry

# In production, prefer Entra ID auth or a key stored in Azure Key Vault
client = AnthropicFoundry(api_key=os.environ["ANTHROPIC_FOUNDRY_API_KEY"], resource="my-foundry-resource")

SYSTEM = "You help data engineers. Explain Azure Data Factory failures briefly. Never invent details; say if unsure."

def explain_failure(run_summary: str, error_text: str) -> str:
    response = client.messages.create(
        model="claude-opus-5-5",  # your Foundry deployment name
        max_tokens=4000,
        system=SYSTEM,
        messages=[{"role": "user", "content":
            f"<pipeline_run>{run_summary}</pipeline_run>\n<error>{error_text}</error>\n"
            "Summarise for the on-call engineer. Give the likely cause and 2-3 checks or fixes."}],
    )
    return "".join(b.text for b in response.content if b.type == "text")


      
The client class follows Anthropic’s SDK docs for Foundry (pip install anthropic). In Foundry, the model value is your deployment name, which defaults to the Claude model ID.

Testing, limits and responsible use

      
How to know your AI app works, where models still go wrong, and how to use them responsibly.

    

    
Photo: U.S. Air Force photo/Staff Sgt. Chris Willis · Wikimedia Commons · Public domain

  


  

    
A model that is right 95% of the time is amazing in a demo and dangerous in production, unless you know where the other 5% hides.

    

      
How models like this work AI apps don’t give the same output every time, and they can fail in surprising ways. So instead of a few manual tries, teams build an : a set of realistic test inputs, a way to grade each answer, and a score to track every time the prompt, model or data changes.

      
    
        
  1. Collect 50–200 real-looking inputs, including tricky and edge cases.
    2. 
        
  2. Decide what “good” means: exact checks (valid JSON, right category), rubric scores, or human review.
    3. 
        
  3. Run and score on every change. Never ship a change that lowers the score.
    4. 
        
  4. Watch production: sample real conversations, collect feedback, add new failures to the eval.
    5.
